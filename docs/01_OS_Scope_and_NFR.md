# Занятие 1. Определение границ операционной системы и разработка нефункциональных требований

## 1. Название и концепция ОС

Название учебной системы — **StudentOS**.

StudentOS — программная модель основных механизмов операционной системы. Она создаётся для учебной практики: на простом коде можно увидеть, как командная оболочка обращается к системным вызовам, как ядро проверяет пользователя и ресурсы, а данные сохраняются в SQLite.

Система моделирует пользователей, процессы, условную память, файловую систему, права доступа, системные вызовы, журнал и командную оболочку. Python выбран из-за простого синтаксиса и наличия нужных модулей в стандартной библиотеке. SQLite используется как компактное хранилище, не требующее отдельного сервера.

Архитектура проекта монолитная: все основные подсистемы находятся в одном Python-проекте и работают через общее ядро и одну базу данных.

## 2. Границы системы

### Входит в систему

1. **Управление процессами.** Можно создать учебный процесс, посмотреть список процессов и завершить его. Процессы хранят имя, состояние, владельца и объём условной памяти.
2. **Управление памятью.** Для процессов учитывается условный объём памяти в мегабайтах и общий лимит системы.
3. **Файловая система SQLite.** Учебные файлы хранятся в таблице `files`: путь, содержимое, владелец и дата создания.
4. **Пользователи.** Учётные записи хранятся в таблице `users`, вход выполняется по логину и паролю.
5. **Права доступа.** Владелец управляет своими объектами, администратор имеет расширенные права. Обычный пользователь не может изменять файлы администратора.
6. **Системные вызовы.** Операции оболочки выполняются через функции `sys_*`.
7. **Командная оболочка.** Пользователь вводит команды в текстовом интерфейсе.
8. **Журналирование.** Каждый системный вызов записывается в `syscalls_log` с аргументами, пользователем, результатом и временем.

### Не входит в систему

1. **Настоящая загрузка ОС.** Проект запускается внутри Windows/Linux как программа, поэтому загрузчик не нужен.
2. **Аппаратные драйверы.** Работа с конкретным оборудованием выходит за рамки учебной модели.
3. **Реальные аппаратные прерывания.** Они требуют низкоуровневого кода и доступа к аппаратуре.
4. **Настоящая виртуальная память.** В StudentOS память только моделируется числом в МБ.
5. **Сетевые протоколы.** Сеть не нужна для целей первой практической работы.
6. **Графический интерфейс.** Для демонстрации механизмов достаточно текстовой оболочки.
7. **Управление настоящим процессором.** Планирование CPU выполняет реальная ОС, а StudentOS только имитирует процессы.
8. **Настоящий доступ к секторам диска.** Учебная файловая система хранится в SQLite и не работает с физическими секторами.

## 3. Сценарии использования

### Сценарий 1. Вход пользователя

**Действующее лицо:** пользователь.

**Последовательность:**

```text
Shell → sys_login() → Kernel → проверка SHA-256 пароля → SQLite(users)
→ syscalls_log → возврат результата в Shell
```

**Системные вызовы:** `sys_login`.

**Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `db.py`, SQLite.

### Сценарий 2. Создание файла

**Действующее лицо:** вошедший пользователь.

**Последовательность:**

```text
Shell → sys_create() → Kernel → проверка входа → SQLite(files)
→ syscalls_log → Shell
```

**Системные вызовы:** `sys_create`.

**Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `db.py`, SQLite.

### Сценарий 3. Чтение файла

**Действующее лицо:** пользователь или администратор.

**Последовательность:**

```text
Shell → sys_read() → Kernel → проверка владельца/роли
→ SQLite(files) → syscalls_log → Shell
```

**Системные вызовы:** `sys_read`.

**Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `db.py`, SQLite.

### Сценарий 4. Запуск процесса

**Действующее лицо:** вошедший пользователь.

**Последовательность:**

```text
Shell → sys_exec() → Kernel → проверка лимита процессов и памяти
→ SQLite(processes) → syscalls_log → Shell
```

**Системные вызовы:** `sys_exec`.

**Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `db.py`, SQLite.

### Сценарий 5. Просмотр процессов

**Действующее лицо:** пользователь.

**Последовательность:**

```text
Shell → sys_ps() → SQLite(processes) → syscalls_log → Shell
```

**Системные вызовы:** `sys_ps`.

**Модули:** `shell.py`, `syscalls.py`, `db.py`, SQLite.

### Сценарий 6. Завершение процесса

**Действующее лицо:** владелец процесса или администратор.

**Последовательность:**

```text
Shell → sys_kill() → Kernel → проверка владельца/роли
→ SQLite(processes: state=terminated) → syscalls_log → Shell
```

**Системные вызовы:** `sys_kill`.

**Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `db.py`, SQLite.

### Сценарий 7. Выделение памяти

**Действующее лицо:** владелец процесса или администратор.

**Последовательность:**

```text
Shell → sys_alloc() → Kernel → проверка процесса, прав и общего лимита памяти
→ SQLite(processes.memory) → syscalls_log → Shell
```

**Системные вызовы:** `sys_alloc`.

**Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `db.py`, SQLite.

### Сценарий 8. Просмотр журнала системных вызовов

**Действующее лицо:** администратор.

**Последовательность:**

```text
Shell → sys_logs() → Kernel → проверка роли admin
→ SQLite(syscalls_log) → запись sys_logs в журнал → Shell
```

**Системные вызовы:** `sys_logs`.

**Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `db.py`, SQLite.

### Сценарий 9. Получение списка пользователей

**Действующее лицо:** пользователь.

**Последовательность:**

```text
Shell → sys_get_users() → SQLite(users) → syscalls_log → Shell
```

**Системные вызовы:** `sys_get_users`.

**Модули:** `shell.py`, `syscalls.py`, `db.py`, SQLite.

### Сценарий 10. Завершение работы системы

**Действующее лицо:** администратор.

**Последовательность:**

```text
Shell → sys_shutdown() → Kernel → проверка роли admin
→ установка флага shutdown_requested → syscalls_log → завершение Shell
```

**Системные вызовы:** `sys_shutdown`.

**Модули:** `shell.py`, `syscalls.py`, `kernel.py`, `db.py`, SQLite.

## 4. Нефункциональные требования

| ID | Категория | Требование | Метрика | Метод проверки |
|---|---|---|---|---|
| P-1 | Производительность | Среднее время простого системного вызова должно быть не более 50 мс на учебном ПК | ≤ 50 мс | 100 запусков + `time.perf_counter()` |
| P-2 | Производительность | Система должна хранить не менее 10 одновременно работающих процессов | ≥ 10 процессов | Запустить 10 процессов и выполнить `ps` |
| P-3 | Производительность | Оболочка должна запускаться не более чем за 2 секунды после старта Python | ≤ 2 с | Замер времени запуска |
| P-4 | Производительность | Вывод списка до 100 записей журнала не должен занимать более 1 секунды | ≤ 1 с | `logs 100` + секундомер/замер |
| P-5 | Производительность | Инициализация уже существующей базы должна выполняться не более чем за 1 секунду | ≤ 1 с | Повторный `python src/db.py` + замер |
| R-1 | Надёжность | Ошибка пользовательской команды не должна завершать оболочку | 0 аварийных завершений в 20 ошибочных командах | Последовательный ввод неверных команд |
| R-2 | Надёжность | Ошибка процесса должна затрагивать только этот процесс/операцию | Оболочка продолжает работу | Вызвать ошибочный `kill` и затем `help` |
| R-3 | Надёжность | Повторный `init_db()` не должен удалять существующие данные | 100% сохранение тестовой записи | Создать файл, повторить `init_db()`, проверить файл |
| R-4 | Надёжность | Попытка чтения отсутствующего файла должна возвращать понятную ошибку | Ошибка без traceback в Shell | `cat /missing.txt` |
| R-5 | Надёжность | Превышение лимита памяти должно блокироваться без повреждения БД | 0 записей сверх лимита | Запросить память выше 256 МБ и проверить `mem` |
| S-1 | Безопасность | Пароли должны храниться только как SHA-256 хэши | 64 hex-символа, нет открытого пароля в БД | Проверка `users.password_hash` |
| S-2 | Безопасность | Обычный пользователь не может изменять файлы администратора | 100% отказ таких попыток | Создать admin-файл и проверить доступ другой ролью |
| S-3 | Безопасность | Каждый системный вызов должен журналироваться | 1 запись на вызов | Выполнить команду и проверить `syscalls_log` |
| S-4 | Безопасность | Просмотр журнала должен быть доступен только роли `admin` | 100% отказ для non-admin | Вызвать `logs` обычным пользователем |
| S-5 | Безопасность | Пароль не должен попадать в аргументы журнала | В журнале вместо пароля `***` | Выполнить `login` и проверить `arguments` |
| M-1 | Поддерживаемость | Код должен быть разделён минимум на 5 смысловых модулей | ≥ 5 модулей | Проверка папки `src` |
| M-2 | Поддерживаемость | Один учебный модуль желательно держать до 300 строк | ≤ 300 строк для основных файлов | Подсчёт строк |
| M-3 | Поддерживаемость | Все основные функции должны иметь понятные имена | 100% основных функций читаемы по названию | Код-ревью преподавателем |
| M-4 | Поддерживаемость | Повторяющееся журналирование должно быть вынесено в общий помощник | 1 общий механизм `_logged_call` | Проверка `syscalls.py` |
| M-5 | Поддерживаемость | Пути проекта должны строиться через `pathlib` | 100% основных путей через `Path` | Проверка `config.py` |
| U-1 | Ресурсоёмкость | Проект должен работать на Python 3.10+ | Python ≥ 3.10 | `python --version` |
| U-2 | Ресурсоёмкость | Внешний сервер базы данных не требуется | 0 внешних серверов | Проверка архитектуры |
| U-3 | Ресурсоёмкость | Для хранения используется один локальный файл SQLite | 1 файл БД | Проверка `db/os.sqlite` |
| U-4 | Ресурсоёмкость | Обязательные сторонние Python-пакеты отсутствуют | 0 пакетов | Отсутствие `pip install`/requirements |
| U-5 | Ресурсоёмкость | Условный лимит памяти StudentOS не должен превышать 256 МБ | ≤ 256 МБ | Команда `mem` и `config.py` |

## 5. Анализ рисков

| № | Риск | Вероятность | Последствия | Минимизация |
|---|---|---|---|---|
| 1 | Нехватка времени | Средняя | Не все функции будут закончены | Сначала реализовать обязательный минимум, затем дополнительные команды |
| 2 | Блокировки SQLite | Низкая | Временная ошибка записи | Короткие транзакции, `with` для соединений, timeout=5 |
| 3 | Ошибки системных вызовов | Средняя | Неверный результат команды | Единый обработчик `_logged_call` и тестирование команд |
| 4 | Отсутствие обработки исключений | Средняя | Падение оболочки | `try/except` в главном цикле Shell |
| 5 | Потеря целостности проекта | Низкая | Удаление/рассинхронизация файлов | Git и регулярные коммиты |
| 6 | Повреждение базы | Низкая | Потеря учебных данных | Простая схема, резервная копия файла БД перед изменениями |
| 7 | Ошибки прав доступа | Средняя | Чужой пользователь получает доступ к объектам | Централизованные проверки в `Kernel` |
| 8 | Чрезмерное усложнение проекта | Средняя | Код трудно объяснить преподавателю | Только Python stdlib + SQLite, без потоков, драйверов и web-фреймворков |

## 6. Описание прототипа

### Реализованные модули

- `config.py` — имя ОС, версия, пути, лимиты процессов и памяти.
- `db.py` — подключение к SQLite, создание таблиц и администратора.
- `kernel.py` — текущий пользователь, аутентификация, права и контроль ресурсов.
- `syscalls.py` — учебные системные вызовы и журналирование.
- `shell.py` — команды пользователя и обработка ошибок.

### Как проверить проект

Открыть терминал в корне `my_os`:

```bash
python --version
python src/db.py
python -m src.shell
```

Затем в оболочке выполнить:

```text
help
echo Hello
users
login admin admin123
whoami
touch /demo.txt "Привет из StudentOS"
cat /demo.txt
write /demo.txt "Изменённый текст"
run demo 20
ps
mem
logs 20
exit
```

После этого открыть файл:

```text
db/os.sqlite
```

и проверить таблицу:

```text
syscalls_log
```

В журнале должны быть, в том числе, записи `sys_echo` и `sys_get_users`.

## 7. Словарь терминов

1. **Операционная система** — программа, которая управляет ресурсами компьютера и предоставляет сервисы приложениям.
2. **Ядро** — центральная часть ОС, которая управляет ресурсами и выполняет системные операции.
3. **Kernel Space** — область, где в настоящей ОС работает ядро с повышенными правами.
4. **User Space** — область выполнения обычных пользовательских программ с ограниченными правами.
5. **Системный вызов** — запрос программы к функциям ядра.
6. **Процесс** — выполняемая программа с собственным состоянием и ресурсами.
7. **Поток** — отдельная последовательность выполнения внутри процесса.
8. **Дескриптор** — числовой или логический идентификатор открытого ресурса.
9. **Планировщик** — механизм ОС, который определяет порядок выполнения процессов/потоков.
10. **Виртуальная память** — механизм отображения адресного пространства процесса на физическую память и диск.
11. **Страница памяти** — блок фиксированного размера, используемый системой виртуальной памяти.
12. **Файловая система** — способ организации, хранения и доступа к файлам.
13. **Аутентификация** — проверка, кем является пользователь.
14. **Авторизация** — проверка, какие действия разрешены пользователю.
15. **Хэширование** — преобразование данных в строку фиксированной длины; применяется, например, для хранения паролей.
16. **SQLite** — встраиваемая реляционная база данных, которая хранится в одном локальном файле.
17. **Монолитная архитектура** — подход, при котором основные части системы находятся в одном приложении и тесно взаимодействуют между собой.
